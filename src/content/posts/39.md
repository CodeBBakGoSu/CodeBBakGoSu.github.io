특히 사용량, 모델 스위칭 피로, 작은 수정 작업의 정확도 측면에서 차이가 컸다.

## 내 업무 환경: 스타트업 인턴으로 MVP를 빠르게 구현하는 역할

나는 스타트업에서 인턴으로 일하고 있다. 내가 맡은 부분은 빠르게 MVP를 구현하는 일이다.  
0에서 시작하는 작업도 있지만, 대부분의 작업은 기존 코드와 컨벤션에 맞춰 동작하도록 수정하는 일이다.  
이때 나는 막연히 Claude Code를 사용했다.(이하 CC)

## Claude Code를 쓰면서 불편했던 점

Opus는 정말 강력한 모델이다. 대부분의 작업을 해결해주고, 꽤 알아서 잘해주는 모델이었다.  
하지만 문제가 있다. 월 20달러 플랜에서는 자유롭게 사용하기가 어렵다.

보통 워크플로우는 이렇게 된다.

플랜을 짜고 -> 확인하고 -> 다시 플랜을 짠다 -> 플랜이 완벽해 보이면 플랜대로 코드를 짜라고 시킨다 -> 테스트를 해본다

따라서 이 과정을 거칠 때마다 모델을 다르게 사용하게 된다.  
플랜을 짤 때는 Opus, 코드를 짤 때는 Sonnet을 썼다.  
일단 모델을 바꿔가며 써야 하는 것 자체가 가장 짜증났다.

모델을 바꿔가면서 코딩을 하는 이유는 사용량 한도가 엄청나게 부족하기 때문이다.  
Opus로 실행시키면 정말 감질맛 나게, 이제 코딩이 조금 될랑 말랑 할 때쯤 5시간 제한에 걸린다.

![클로드 코드 사용량](/images/posts/39/2.png)

이렇게 바로바로 확인하면서 코딩해야 했고, 워크트리를 이용해 병렬로 처리하면 훨씬 더 많은 토큰이 소모됐다.

이 밖에도 한 오류에 꽂혀서 비슷한 작업을 반복한다거나, “알아서 잘 해줘” 하면 잘해주는데  
무언가 특별한 걸 시켰을 때는 분명히 명시했는데도 넘어가는 경우가 많았다.  
특히 한 번에 여러 가지를 시키면 그런 경우가 더 잦았다.  
하지만 결정적인 건 따로 있었다.

### 월에 3만원인데 오푸스가 너무 비싸다.

특히 openclaw에 연결했을 때는 30분이 안 돼서 5시간 limit이 오링 난 적도 있었다.

## Claude Code 대안으로 OpenCode와 Codex를 찾은 이유

그래서 다른 코딩 툴을 찾아 헤맸다. OpenCode와 Codex가 그 후보였다.

## OpenCode를 실무에 쓰며 느낀 장단점

![](/images/posts/39/3.png)

당연히 oh-my-opencode를 연결해서 사용했다.  
나름 어떤 서브에이전트에 어떤 모델을 연결할까 고민하는 재미도 있었다.

고민하는 것도 재밌었고, JSON 설정 파일을 여러 번 고쳐가면서 나만의 coding agent를 만들어가는 느낌이 들었다.

하지만 내 업무는 어떤 걸 어떻게 고쳐야 하는지 어느 정도는 알아야 하면서도, 너무 많은 범위를 건드리면 안 되는 일이 많았다.  
제로베이스에서 시작하는 작업에는 좋을 수 있겠지만, 약간의 수정 사항에도 시간이 엄청 오래 걸렸다.

가끔은 SubAgent가 삑나서 또 기다려야 했고, 업데이트 이후 오류도 있었다.  
이런 날것의 오픈소스 느낌이 피곤하게 다가왔다.

또한 subagent의 병렬 처리를 조합하는 오케스트레이션을 가장 잘하는 모델이 Opus였는데, Opus는 비쌌다.  
Claude Code 20달러 요금제를 쓰면 더욱 부족했다.  
나중에는 Codex를 연결해서 사용했다.

## Codex CLI를 써보고 정착한 이유

![](/images/posts/39/4.webp)

운 좋게도 Codex app이 출시되기 직전, Codex CLI를 사용해보기로 마음먹었다.  
일단 가장 마음에 들었던 것은 Codex 전용 모델에서 생각의 깊이만 조절해가며 사용해도 사용량이 꽤 넉넉하다는 점이었다.

두 배 이벤트 전에도 넉넉했는데, 2026년 4월 2일까지 사용량 두 배 이벤트를 진행 중이라 더욱 여유로웠다.

이 부분이 가장 마음에 들었다.

또한 도메인 지식이 더 많았고, 필요한 만큼만 코드를 수정해 내 업무 task에 잘 맞았다.

예를 들어 기존 로그인 플로우에서 에러 처리만 수정하고, UI 문구와 API 응답 형식을 맞춰야 하는 작업이 있었다.  
이때 내가 원한 건 전체 구조를 다시 설계하는 게 아니라, 이미 있는 흐름 안에서 필요한 부분만 정확하게 바꾸는 것이었다.

물론 제로베이스로 크게 설계해야 하거나, 긴 컨텍스트를 바탕으로 복잡한 오케스트레이션을 해야 하는 작업에서는 Claude Code, 특히 Opus의 강점이 더 크게 느껴질 수 있다.  
다만 내 업무는 거기보다 작고 빠른 수정이 많았고, 그래서 우선순위가 달랐다.

## 정리하며

좋은 모델을 쓰는 것과, 나한테 맞는 도구를 쓰는 건 다르다고 느꼈다.  
Claude Code는 분명 강력했고, OpenCode는 재밌었다. 하지만 내 실무에서는 “얼마나 대단한가”보다  
“얼마나 덜 업무의 연속성을 해치지 않는가”가 더 중요했다.  
빠르게 만들고, 필요한 만큼만 고치고, 기존 코드에 자연스럽게 붙이는 것.  
그 기준에서 지금 내 선택은 Codex다.
